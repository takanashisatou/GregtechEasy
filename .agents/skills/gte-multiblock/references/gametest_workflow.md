# 多方块 GameTest 工作流

先判断是否需要运行测试：纯静态分析交付源码依据；实现改动再验证相关行为。沿用邻近 `@GameTestHolder`、batch、template 与 required 约定。

## 隔离真实结构场地

`empty` 模板只清理模板本身，通常远小于机器。相对高度会加上模板世界坐标；将控制器设成相对 y=160 仍可能碰到自然地形。不能以“本地场地是空气”替代明确的隔离。

1. 确定当前结构相对控制器的边界与世界建筑高度。选择与其他测试结构分离、完整放得下的场地。
2. 清理实际结构范围内的已有方块后再放控制器/autoBuild；仅对测试世界中该夹具的区域执行清场。选择靠近建筑高度上限的场地可以减少地形干扰，但不能替代清场。
3. 回归地形问题时主动放入原先会阻挡结构的方块，证明夹具清理有效，而不是依赖 runner 的世界种子。
4. 创意 `autoBuild` 会保留非空气方块，还可能选择带最大数量限制的可选仓口。验证“0/2/3 个仓口”时，先把自动加入的可选仓恢复为合法外壳，再分别增加数量。
5. 调用真实 pattern 检查。失败输出 `error.getErrorInfo()`、坐标和实际方块，不只打印 error 对象地址；旋转/翻转的后续尝试可能掩盖最初失配位置，必要时核对指定朝向。

参考当前 `PetrochemicalPlantGameTest` 的隔离夹具与 `SuperFusionIIGameTest` 的结构构建方式。不要把某台机器的 44 格范围或固定高度复制给尺寸不同的机器。

## 验证运行而不只验证注册

优先选一条真实注册配方，使用真实控制器和仓口：

- 验证目标条件通过，同时原机器、非目标机器、反向条件及其他环境要求仍保持正确语义。
- 经 `onStructureFormed()` 初始化真实仓口、能力表和电压等级。只手工附加输入 handler 会遗漏 tier 初始化，可能把测试夹具的欠压误报成配方条件失败。
- 从匹配/启动路径验证输入消耗，再验证每 tick 条件、电力和输出；不只检查 recipeTypes 数组是否包含一个类型。
- 完整结构与 IO 单独测试时，明确各自覆盖范围；手工触发 `onRecipeFinish()` 不代表完整持续运行时序也已经覆盖。

## 结果与失败

读取必需测试最终通过结论及 Gradle 退出码；Forge 某些初始化失败可能只返回零退出码。既有 runner 已有最终日志守卫时使用它。

失败先找具体断言，再区分实现错误、场地污染、随机测试假设和启动环境。不同 seed 使同一地形假设失效时，应修正隔离，而不是不停重跑 CI 或降低 required/数量断言。修复后再跑受影响套件；不要因为一个测试夹具修改而刷新生产 JAR。
