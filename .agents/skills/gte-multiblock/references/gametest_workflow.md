# 多方块 GameTest 工作流

沿用同包下已有测试的 `@GameTestHolder`、batch、template 与 required 约定。结构清场参考 `PetrochemicalPlantGameTest`，大型结构构建参考 `SuperFusionIIGameTest`。

## 1. 大结构一定要自己清场

`empty` 模板只清理模板自身那一点点体积，通常远小于多方块。即使把控制器抬到相对 `y=160`，加上模板世界坐标后照样可能撞上自然地形或树冠。

1. 先按当前机器相对控制器的包围盒算出完整占用范围，确认不超世界建筑高度、不和邻近测试撞车。
2. 放控制器和 `autoBuild` 之前，把这片包围盒显式清成空气（别硬抄别的机器的 44 格范围或固定高度，按自己机器尺寸算）。
3. 回归地形干扰 bug 时，在清场前故意放几个阻挡方块，这样才能稳定复现并验证清场有效，不依赖随机种子。
4. 创意 `autoBuild` 有两个坑：**不会清掉原本的非空气方块**，而且会顺手塞进带上限的可选仓口。测「0 / 2 / 3 个特殊仓口」这类数量断言时，先把自动放进去的可选仓换回外壳，再从已知 0 个开始逐个加。
5. 直接调真实 pattern 校验。失败时把 `error.getErrorInfo()`、出错坐标和那个坐标上的真实方块都打出来；注意多方向旋转重试可能会覆盖掉最初的失配点，必要时锁死朝向查。

## 2. 测配方要走真实成型

- 选一条真实注册配方，放真实控制器和仓口，走完整的 `onStructureFormed()` 初始化能力表和电压等级（tier）。只手工挂输入 handler 会漏掉 tier 初始化，把欠压误判成配方条件失败。
- 修条件兼容时，顺手测一下：目标机器能跑、原机器正常、不该跑的机器依然被拦、反向条件和其他环境要求没坏。
- 验证输入确实被消耗、每 tick 条件/电力正常且产出到位，别只测 `recipeTypes` 数组里有没有这个类型。
