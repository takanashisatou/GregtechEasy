# CI/CD конвейер автоматической сборки, упаковки и публикации Maven

GTE создал высокоавтоматизированный **конвейер CI/CD GitHub Actions** с параллельной сборкой нескольких целевых артефактов (файлы конфигурации находятся в `.github/workflows/sync-build.yml` и `release-publish.yml`).

---

## 🔄 Архитектура полного конвейера CI (`sync-build.yml`)

При каждом push кода в ветки `master` / `main` / `satou`, создании PR или срабатывании Release Tag, GitHub Actions автоматически выполняет следующий стандартный конвейер:

```mermaid
flowchart TD
    A[Push кода / срабатывание Tag] --> B[Checkout рекурсивных подмодулей и настройка JDK 21 / Python 3.11 / Go]
    B --> C[Gradle инкрементальная синхронизация художественных ассетов Blockbench syncBlockbenchAssets]
    C --> D[Многомодульная высокопараллельная компиляция и автоматическое тестирование GameTest]
    D --> E[Копирование сгенерированных Jar в overrides/mods и сбор в build/artifacts]
    E --> F[Запуск opencode_translate.py для полного/инкрементального AI-перевода интернационализации]
    F --> G[Стандартная упаковка Packwiz: пакет CurseForge + патч manifest для Java 21]
    G --> H[Python сборка клиентского пакета со всеми модами GTE-FullMod]
    H --> I[Packwiz экспорт чистого серверного пакета Server]
    I --> J[Загрузка всех артефактов Release в хранилище Actions Artifacts]
    J --> K[Сборка статического Maven-репозитория и развертывание на GitHub Pages (gh-pages)]
    J --> L[При срабатывании Tag: автоматическая публикация на платформу CurseForge]
```

## 📦 Подробное описание трех основных задач упаковки

### 1. Стандартный пакет CurseForge и патч Java 21
- **Экспорт Packwiz**: запуск `packwiz curseforge export` для генерации стандартного пакета.
- **Автоматический патч manifest.json**: для решения проблемы, когда некоторые сторонние лаунчеры при разборе пакета CurseForge по умолчанию назначают Java 17, CI автоматически распаковывает zip, с помощью Python-скрипта **принудительно записывает** `minecraft.javaVersion` и верхнеуровневый `javaVersion` в `manifest.json` как **21**, а затем переупаковывает.

### 2. Клиентский пакет со всеми модами для игроков (`build_full_mod_pack.py`)
- Python-скрипт автоматически извлекает последние основные Jar из `build/libs/` каждого модуля.
- Автоматически объединяет ключевые расширяющие моды из `modules/gtecore/gradle/libs/`.
- Упаковывает все конфигурации, скрипты KubeJS, руководство Пачули в плоский архив `GTE-FullMod-*.zip` (на верхнем уровне `mods/`, `config/`, `defaultconfigs/`, `kubejs/`) со встроенным руководством по установке на китайском языке `README_安装必看.txt`.

### 3. Экспорт серверного пакета (`packwiz server export`)
- Автоматически удаляет клиентские оптимизационные моды (например, 3D-слой скинов, шейдеры, привязки клавиш и т.д.), создавая чистый серверный пакет, который можно напрямую развернуть на производственных серверах Linux/Windows.

## 🌐 Развертывание статического Maven-репозитория на GitHub Pages

Конвейер через задачу `publish` Gradle собирает все подмодули (`gtecore`, `gtm-reborn`, `gt--`) в стандартные Maven-артефакты и развертывает их в ветку `gh-pages`:

```groovy
// Прямое подключение Maven-репозитория GTE в сторонних модах или проектах разработки
repositories {
    maven {
        name = "GTE GitHub Pages Maven"
        url = "https://takanashisatou.github.io/GregtechEasy/"
    }
}

dependencies {
    implementation fg.deobf("org.satou.gtecore:gtecore-1.20.1:1.0.0")
}
```

## 🏷️ Ручная публикация и рабочий процесс версионирования (`release-publish.yml`)

Проект использует стандартизированный процесс Git Release:
1. Вручную запустите **Manual Publish Release** на странице GitHub Actions, введите номер версии (например, `2.3.0`).
2. Рабочий процесс автоматически создает PR `dev -> release`, выполняет проверку CI и автоматически выполняет Squash Merge.
3. Автоматически создает Git Tag `v2.3.0` в ветке `release` и отправляет его.
4. Событие push Tag автоматически запускает `sync-build.yml`, окончательно завершая публикацию артефактов по всем каналам.
